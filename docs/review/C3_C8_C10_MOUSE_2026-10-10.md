## C3 — mode-2 mouse text capture (OLEACC) — **confirms the row, and tightens it**

`FUN_00404901` decompiles to exactly the documented chain:

```
GetCursorPos(&local_14)
AccessibleObjectFromPoint(ptScreen, &local_c, &local_24)
(*local_c->lpVtbl->get_accName)(local_c, varChild, pszName)      // primary
  -- when get_accName fails (SysStringLen == 0) --
(*local_c->lpVtbl->lpVtbl->get_accValue)(local_c, varChild_00, pszValue)
Ordinal_6/Ordinal_7/Ordinal_9 = SysFreeString / SysStringLen wrappers
```

Return value is `*(int *)(*this - 0xc) != 0` — i.e. "did the CString end up
non-empty". So the row's `else get_accValue` clause is right, and the priority is
`get_accName` → fallback `get_accValue`.

`AccessibleObjectFromPoint` has exactly **2 callers** program-wide, so this is the
only OLEACC text-capture site.

**Port gap (unchanged, but now precisely bounded):** the port's
`mouse_capture.py` implements the *trigger* (click down+up in place) via a
`WH_MOUSE_LL` hook and hands `(x, y)` to a callback. It calls back into the
translate task but never performs OLEACC text extraction at the cursor. So the
port reproduces C8's trigger, not C3's payload.

## C8 — RawInput mouse → normalized click — **confirms the row exactly**

`FUN_00417E4E`:

```
GetRawInputData(param_3, 0x10000003 /*RID_INPUT mouse*/, local_34, &0x28, 0x10)
GetSystemMetrics(0x17 /*SM_SWAPBUTTON*/)
  -> buttons swapped: (flags & 1) != 0  => 0x201  (see LAB_00417ebc)
  -> else:         (flags & 2) != 0
  -> swapped:      (flags & 4) != 0  => 0x201
  -> else:         (flags & 8) != 0
  -> neither       => return 0
  -> 0x202  (WM_LBUTTONUP)
GetCursorPos(&local_54); GetTickCount(); SetRectEmpty(&local_44)
FUN_004193F6(this, iVar2, &local_54)
```

`GetSystemMetrics(0x17)` is `SM_SWAPBUTTON` — this is the documented
"normalize to `0x201`/`0x202` using `GetSystemMetrics(0x17)` handedness", now
observed in the actual branch structure rather than just the row's prose.

`FUN_004193F6` (the consumer) confirms the down-side state machine:
`IsWindow(this+0xe90)`, `FUN_00438c02` / `FUN_0043A8C4` guards, then
`FUN_00450DD2(x,y)` (WindowFromPoint), compares against `this+0x1280` (own
window), exclusion check `FUN_004631DE(&DAT_005494b0, hwnd)` (or
`FUN_004630C5` when `DAT_005494d0`), `GetWindowRect` + `PtInRect`, and records
`{pt, hwnd}` at `this+0x17f8` / `this+0x1804`.

The port's `WH_MOUSE_LL` hook reproduces the *effect* (down+up in one place ⇒
selection click) but not the mechanism: it never consults `SM_SWAPBUTTON`, never
does the own-window skip, and never runs the exclusion list. A left-handed
Windows user (swapped buttons) would get the same trigger from the port and a
different one from native.

## C10 — cursor hook / mouse icon — **the row's prose is too strong; narrow it**

The row currently claims "no `SetCursor`/cursor-icon hook exists **anywhere** in
the enumerated input path (only wndclass cursors)". The "in the input path"
qualifier is what saves it, but the blanket "only wndclass cursors" does not
survive the real image:

| API | callers |
|-----|---------|
| `SetCursor` | **14** |
| `LoadCursorW` | **12** |
| `CopyImage` | 2 |
| `SetCursorPos` | 0 |
| `GetCursorInfo` | 0 |
| `DrawIcon` | 0 |
| `SetClassLongW` | 0 |

So `SetCursor`/`LoadCursorW` are genuinely called, and `CopyImage` is too. But
their call sites cluster at `0x4373xx`, `0x437axx`, `0x50d4xx` — the
dialog/window-class region (`FUN_004377CB` is the screen-capture overlay, per row
K2), **not** the mouse-capture chain `FUN_00417E4E → FUN_004193F6 → FUN_00404901`,
which contains no cursor call at all.

The load-bearing claim for C10 is therefore the narrower and still-true one:

> The mouse-selection capture path (`00417E4E` → `004193F6` → `00404901`) contains
> no `SetCursor`, no `LoadCursorW`, and no cursor-icon rendering. Cursor changes
> elsewhere in the program belong to dialog/window-class and overlay code.

`SetWindowsHookExW` has **0** callers — the port's `WH_MOUSE_LL` approach is not
how native does it (native uses `WM_INPUT`/RawInput, matching C8). Not a defect,
worth recording.

## What this means for the port states

- **C3**: `not-started` is honest → the OLEACC payload is genuinely absent. Keep
  it `not-started` and note the port stops at the trigger.
- **C8**: `not-started` is **too harsh**. The trigger (down+up ⇒ click) is
  ported and `mouse_capture.py` is exercised; the *fidelity deltas* are now
  enumerated (no `SM_SWAPBUTTON`, no own-window skip, no exclusion check, and no
  RawInput). This is `ported`, not `not-started`.
- **C10**: row prose needs the narrowing above before it can be promoted.

No row state changed by this document. It records the evidence so the row edits
are a decision made on measured facts rather than on doc prose.
