## C3 — mode-2 mouse text capture (OLEACC) — **confirms the row, and tightens it**

`FUN_00404901` decompiles to exactly the documented chain:

```
GetCursorPos(&local_14)
AccessibleObjectFromPoint(ptScreen, &local_c, &local_24)
(*local_c->lpVtbl->get_accName)(local_c, varChild, pszName)      // primary
  -- when get_accName fails (SysStringLen == 0) --
(*local_c->lpVtbl->lpVtbl->get_accValue)(local_c, varChild_00, pszValue)
Ordinal_6/Ordinal_7/Ordinal_9 = SysFreeString / SysStringLen wrappers
```

Return value is `*(int *)(*this - 0xc) != 0` — i.e. "did the CString end up
non-empty". So the row's `else get_accValue` clause is right, and the priority is
`get_accName` → fallback `get_accValue`.

`AccessibleObjectFromPoint` has exactly **2 callers** program-wide, so this is the
only OLEACC text-capture site.

### C3a — the fallback is `SysStringLen(name) == 0`, not an HRESULT check

Re-disassembled 2026-10-10 (later, with `tools/ghidra/DisasmNamed.java`) and
**this doc's own §C3 line "when get_accName fails" is imprecise.** The branch is
not taken on the HRESULT of `get_accName`; it is taken on the *string*:

```
00404983   CALL dword ptr [ECX + 0x28]     ; get_accName(this, varChild, &pszName)
00404989   CALL dword ptr [0x0050d3e8]     ; SysStringLen(pszName)
00404991   JZ 0x0040499f                   ; == 0  ->  fall through to get_accValue
00404993   PUSH dword ptr [EBP + -0x4]     ; non-empty: attach to the CString
00404998   CALL 0x00401ea9                 ;   and skip get_accValue
...
0040499f   MOV EAX,dword ptr [EBP + -0x8]  ; the IAccessible object again
004049b9   CALL dword ptr [ECX + 0x2c]     ; get_accValue(this, varChild, &pszValue)
```

So a `get_accName` that *succeeds* but returns a zero-length string still falls
through to `get_accValue`. `HRESULT` is not consulted at all for the branch —
`GET_LAST_ERROR`-style success is irrelevant; only emptiness matters. That is a
sharper rule than "fails", and it is the one the port must match.

### C3b — the vtable offsets, read from the instruction rather than the decompile

`tools/ghidra/DecompileNamed.java` renders these as
`(*pIVar2->get_accName)(...)`, which *presumes* the answer. The raw instructions
carry the offset literally:

| Instruction | Offset | Slot (0-based, 32-bit ptr) | Method |
|---|---|---|---|
| `00404983  CALL dword ptr [ECX + 0x28]` | `0x28` = 40 | **10** | `get_accName` |
| `004049b9  CALL dword ptr [ECX + 0x2c]` | `0x2c` = 44 | **11** | `get_accValue` |
| `00404a02  CALL dword ptr [EDX + 0x8]` | `0x8` = 8 | **2** | `IUnknown::Release` |

The port's `mouse_capture.cursor_text()` uses `vtbl[10]` and `vtbl[11]`
(`qtranslate/mouse_capture.py:85-90`), and calls `ole32.Release` in its
`finally`. **The indices match the binary exactly** — this is the one C3 claim
that was guessable-looking and is now measured.

### C3c — the import thunks, resolved

The `CALL dword ptr [0x0050d...]` targets are IAT slots. Resolving each through
the PE import directory (offsets into `docs/review/artifacts/QTranslate.6.10.0.exe`):

| IAT VA | Import | Call site |
|---|---|---|
| `0x50d640` | `GetCursorPos` | `00404925` |
| `0x50d410` | `AccessibleObjectFromPoint` | `00404958` |
| `0x50d3e8` | OLEAUT32 **ordinal 7** = `SysStringLen` | `00404989`, `004049bf` |
| `0x50d3ec` | OLEAUT32 **ordinal 6** = `SysFreeString` | `004049d6`, `004049e8` |
| `0x50d3e4` | OLEAUT32 **ordinal 9** = `SysStringByteLen` | `004049f2` |
| `0x50d410`… | OLEAUT32 **ordinal 8** = `SysAllocString` | via `_func_14674` |

`OLEAUT32.dll` is imported **entirely by ordinal** (15 entries, ordinals 2/4/6/7/
8/9/10/11/12/16/146/200/201/202/411), which is why Ghidra names them
`Ordinal_6/7/8/9` rather than `SysFreeString`/`SysStringLen`. The ordinal →
name mapping in §C3 is therefore confirmed against the import table, not
inferred from the call sites.

**Correct in binary, corrected in prose:** the disassembly shows
`CALL 0x0050d3d0` at `00404958`, which resolves to `AccessibleObjectFromPoint` —
confirming the chain's second step.

### C3d — **the port gap this section claimed is closed**

> **This paragraph corrects the one above it, which is wrong.**
> "Never performs OLEACC text extraction at the cursor" was false when written
> and is false now. `cursor_text()` landed in the *same commit* as this document
> (`538b968`) — so the paragraph described the pre-implementation state and was
> never re-read after the code it describes was written.`qtranslate/mouse_capture.py:67-117` implements the full chain:
> `AccessibleObjectFromPoint` → `vtbl[10]` `get_accName` → `SysStringLen` gate →
> `vtbl[11]` `get_accValue` → `SysStringLen` gate, with `SysFreeString` in a
> `finally` and `ole32.Release` after. `app.py:3871` routes mode 2
> (`General.MouseMode == 2`, native `FUN_004183bd`) through it, falling back to
> the clipboard only when the read is empty.

**Two fidelity deltas that remain, now measured rather than suspected:**

1. **`.strip()` is applied to the returned text; native does not strip.** Native
   attaches the BSTR to a `CString` as-is (`CALL 0x00401ea9`) and gates only on
   *length*. A leading-space accessible name would translate differently.
2. **`hr < 0` early-returns.** Native's `JNS 0x00404969` at `00404960` is the same
   check, so this one *does* match — native returns `false` when
   `AccessibleObjectFromPoint` fails, and so does the port.

The `.strip()` is worth a deliberate decision rather than a silent one: it makes
the empty-read check insensitive to whitespace, which is friendlier for the
clipboard-fallback branch, but it is not what the binary does.

## C8 — RawInput mouse → normalized click — **confirms the row exactly**

`FUN_00417E4E`:

```
GetRawInputData(param_3, 0x10000003 /*RID_INPUT mouse*/, local_34, &0x28, 0x10)
GetSystemMetrics(0x17 /*SM_SWAPBUTTON*/)
  -> buttons swapped: (flags & 1) != 0  => 0x201  (see LAB_00417ebc)
  -> else:         (flags & 2) != 0
  -> swapped:      (flags & 4) != 0  => 0x201
  -> else:         (flags & 8) != 0
  -> neither       => return 0
  -> 0x202  (WM_LBUTTONUP)
GetCursorPos(&local_54); GetTickCount(); SetRectEmpty(&local_44)
FUN_004193F6(this, iVar2, &local_54)
```

`GetSystemMetrics(0x17)` is `SM_SWAPBUTTON` — this is the documented
"normalize to `0x201`/`0x202` using `GetSystemMetrics(0x17)` handedness", now
observed in the actual branch structure rather than just the row's prose.

`FUN_004193F6` (the consumer) confirms the down-side state machine:
`IsWindow(this+0xe90)`, `FUN_00438c02` / `FUN_0043A8C4` guards, then
`FUN_00450DD2(x,y)` (WindowFromPoint), compares against `this+0x1280` (own
window), exclusion check `FUN_004631DE(&DAT_005494b0, hwnd)` (or
`FUN_004630C5` when `DAT_005494d0`), `GetWindowRect` + `PtInRect`, and records
`{pt, hwnd}` at `this+0x17f8` / `this+0x1804`.

The port's `WH_MOUSE_LL` hook reproduces the *effect* (down+up in one place ⇒
selection click) but not the mechanism: it never consults `SM_SWAPBUTTON`, never
does the own-window skip, and never runs the exclusion list. A left-handed
Windows user (swapped buttons) would get the same trigger from the port and a
different one from native.

## C10 — cursor hook / mouse icon — **the row's prose is too strong; narrow it**

The row currently claims "no `SetCursor`/cursor-icon hook exists **anywhere** in
the enumerated input path (only wndclass cursors)". The "in the input path"
qualifier is what saves it, but the blanket "only wndclass cursors" does not
survive the real image:

| API | callers |
|-----|---------|
| `SetCursor` | **14** |
| `LoadCursorW` | **12** |
| `CopyImage` | 2 |
| `SetCursorPos` | 0 |
| `GetCursorInfo` | 0 |
| `DrawIcon` | 0 |
| `SetClassLongW` | 0 |

So `SetCursor`/`LoadCursorW` are genuinely called, and `CopyImage` is too. But
their call sites cluster at `0x4373xx`, `0x437axx`, `0x50d4xx` — the
dialog/window-class region (`FUN_004377CB` is the screen-capture overlay, per row
K2), **not** the mouse-capture chain `FUN_00417E4E → FUN_004193F6 → FUN_00404901`,
which contains no cursor call at all.

The load-bearing claim for C10 is therefore the narrower and still-true one:

> The mouse-selection capture path (`00417E4E` → `004193F6` → `00404901`) contains
> no `SetCursor`, no `LoadCursorW`, and no cursor-icon rendering. Cursor changes
> elsewhere in the program belong to dialog/window-class and overlay code.

`SetWindowsHookExW` has **0** callers — the port's `WH_MOUSE_LL` approach is not
how native does it (native uses `WM_INPUT`/RawInput, matching C8). Not a defect,
worth recording.

## What this means for the port states

- **C3**: `not-started` is honest → the OLEACC payload is genuinely absent. Keep
  it `not-started` and note the port stops at the trigger.
- **C8**: `not-started` is **too harsh**. The trigger (down+up ⇒ click) is
  ported and `mouse_capture.py` is exercised; the *fidelity deltas* are now
  enumerated (no `SM_SWAPBUTTON`, no own-window skip, no exclusion check, and no
  RawInput). This is `ported`, not `not-started`.
- **C10**: row prose needs the narrowing above before it can be promoted.

No row state changed by this document. It records the evidence so the row edits
are a decision made on measured facts rather than on doc prose.
