## 1. Why BLOCKED (two independent blocking reasons)

The harness needs **both** a native capture and a port capture under identical
protocol. Each side is blocked separately, for a different reason, and neither
is an artifact the harness itself can work around.

### 1.1 Native side — the executable cannot run on this host

`/Users/tranquangdang21/Downloads/QTranslate.6.10.0.exe` is a **Win32 PE that
cannot execute here**:

| Fact | Value | How verified |
|------|-------|--------------|
| Size | `909 KiB` (930739 bytes) | `ls -la` |
| DOS header | `MZ` | first 2 bytes read |
| PE signature | `PE\0\0` | at `e_lfanew = 0xd8` |
| Target machine | `0x14c` = `IMAGE_FILE_MACHINE_I386` | `Machine` field, read as raw little-endian `<H` |
| Subsystem | `2` = `IMAGE_SUBSYSTEM_WINDOWS_GUI` | `Subsystem` field of the optional header |
| Host CPU | `arm64` (Apple silicon, `Darwin 25.4.0`, `xnu-12377.101.15`) | `uname -a` |

The binary is 32-bit x86 and this machine is ARM64 Darwin. There is **no
runtime that can load it**:

- `wine` — `wine not found`
- `wine64` — `wine64 not found`
- No other Windows emulation layer was found or attempted (a PE loader/Hyper-V
  VM would be a different, much larger claim than "run an .exe").

Additionally the harness's own `capture` command is Windows-only by design —
it uses `PrintWindow` (`PW_RENDERFULLCONTENT`) on a live window, and
`tools/g9_screenshot_diff.py:608-610` short-circuits to `BLOCKED` with exit
`2` when `sys.platform != "win32"`. Every command that was run below was run
to *prove* the blocks, not to produce an image.

### 1.2 Port side — the port UI can be built, but this session cannot capture pixels

The port is **not** blocked by missing tkinter: `uv run --python 3.12 --with
keyboard --with pyperclip --with pillow` created a bare `tk.Tk()` successfully
(so the port UI is constructible here). Pixel capture is blocked, because every
screenshot mechanism on this host fails with the same CoreGraphics error:

```
$ screencapture -x /tmp/…/sc_test.png
could not create image from display
EXIT=1        (no file written)
```

```
$ PIL.ImageGrab.grab()          # falls back to `screencapture -x <tmpfile>`
could not create image from display
CalledProcessError: Command '['screencapture', '-x', '<tmpfile>]' returned
non-zero exit status 1
```

```
$ PIL.ImageGrab.grab(bbox=(34,92,214,292))    # window-relative bbox
could not create image from rect
CalledProcessError … returned non-zero exit status 1
```

The `Assertion failed: (range.location <= dataLength), function
__CFDataValidateRange, file CFData.c, line 219` line seen once during a
launch is a CoreGraphics-side symptom of the same underlying condition, not a
distinct cause.

The root cause is **Screen Recording permission is not granted** in this
session's GUI context: `screencapture` cannot read the display, so no
rectangle of the screen — full or window-relative — can be captured. The TCC
database is not readable to confirm it (`authorization denied`), and the fix
("System Settings → Privacy & Security → Screen Recording → grant, then
restart") is a **human action this session cannot perform**. It is not recorded
as a harness defect: `g9_screenshot_diff.py`'s compare path reported nothing
spurious, it simply never received an image to compare.

> `tools/capture_app.py` therefore also cannot regenerate `screenshots/app.png`
> here. The committed `screenshots/app.png` (530×430 PNG, colortype 2 /
> truecolor) is a **stale artifact from an earlier session on another display**,
> *not* a capture from this machine, and it is **not** used as a baseline.
