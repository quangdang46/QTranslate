So native requests the classic `CLSID_JScript` and names no engine version,
exactly as F13 says. Which DLL resolves that CLSID is an OS/registry
property outside the binary, so no version is claimed — consistent with the
row.

## Why two REA searches returned `[]`, and why that proves nothing

`rea search <binary> F414C260` and `rea search <binary> JScript` both returned
empty result sets. **An empty REA result is not a negative finding.** The
provider search is literal text over Ghidra's defined/string data; a GUID
stored as 16 binary bytes is not a string, and `JScript` appears nowhere as
text **by design** (that absence is itself the claim being tested).

The GUID had to be located by direct byte scan with
`struct.pack("<IHH", ...) + bytes([...])`, which found it at the documented
offset. Recorded because "the tool found nothing" was previously allowed to
stand as evidence in this repo (`GHIDRA_MCP_UNAVAILABLE_2026-10-10.md` makes
the same point about a different tool's silence).

## What this does NOT establish

- No claim about which JScript DLL backs the CLSID on any given machine.
- No port work: F13 stays a documented architectural divergence (the Python
  Extension SDK contract is a class, `EXTENSION_SDK.md` §5), so there is no
  engine to port.
